## 1. 架構與連線方式

```
  Windows 端 Godot 編輯器 / 執行檔
        │  HTTP (HTTPRequest 節點)
        │  base_url = http://172.31.143.82:8000
        ▼
  WSL2 內的 FastAPI 後端 (uvicorn) :8000
        └── api/server.py 內所有 @app.post / @app.get 路由
```

- Godot 跑在 Windows，後端跑在 WSL2，兩者**不是 localhost**。Windows 要連 WSL 內的服務，必須用 **WSL 的虛擬網卡 IP**，不能用 `127.0.0.1`。
- 目前 WSL IP = `172.31.143.82`（用 `hostname -I` 在 WSL 內查）。
- 各 Godot client 的 `@export var api_base_url` 都硬寫成 `http://172.31.143.82:8000`：
  - `src/core/EventChoiceClient.gd`（被動決策 → `/event/choose`）
  - `src/core/BifurcationController.gd`、`BifurcationAPIClient.gd`、`ABTestClient.gd`、`DungeonSim.gd`、`PlayerTestSessionClient.gd`、`PlayableLoopController.gd`、`SurveyPanel.gd`
  - 例外：`PersonalityAPIClient.gd` 與 `RLSessionAPIClient.gd` 寫的是 `127.0.0.1`（若由 Windows Godot 直接呼叫會連不到，須一併改成 WSL IP；目前若這兩個能通，代表是在 WSL 內或有 port forwarding）。

### 後端啟動方式（在 WSL 內）

## 2. 本次故障：「面對事件」按下去回 HTTP 404

### 症狀
在「分身決策（被動）」面板按下「面對事件」，`EventChoiceClient` 收到 `response_code == 404`，
於 `_on_request_completed`（`EventChoiceClient.gd:79-81`）發出 `request_failed("HTTP 404")`。

### 根因（已確認，非前端 bug）
**後端跑的是一個過時的 server process**，啟動時間早於 `/event/choose` 路由被加入原始碼的時間：

| 項目 | 時間 |
|------|------|
| 舊 server process 啟動 | 2026-06-06 03:54:40 |
| `api/server.py` 最後修改 | 2026-06-06 20:34:14 |

排查時對執行中的後端打 `/openapi.json`，發現它**沒有**這三條較新的路由：
- `POST /event/choose`（被動決策）
- `POST /rl_sessions/{id}/apply-event`
- `GET /rl_sessions/{id}/personality`

而原始碼 `api/server.py:1183` 明明有 `@app.post("/event/choose")`。
→ 路徑沒打錯、IP 沒錯、port 沒錯、伺服器有在聽；純粹是**記憶體裡的舊版程式沒有這條 route**，FastAPI 因此回 404。

> 判讀口訣：
> - **連線錯誤 / result != SUCCESS** → IP、port、服務沒開、防火牆問題。
> - **HTTP 404（有回應但找不到路由）** → 多半是後端版本過舊（route 還沒載入）或路徑拼錯。本次屬前者。

### 解決方式
重啟後端，讓它載入最新的 `server.py`：

```bash
# 1. 關掉舊 process（PID 由 ss -tlnp / ps 取得）
kill <舊PID>

# 2. 重新啟動
cd /home/user/personality-dungeon
nohup ./venv/bin/python -m api.server > logs/api_server.log 2>&1 &
```

### 結果（已驗證）
重啟後：
- `GET /openapi.json` 已包含 `/event/choose`、`/rl_sessions/{id}/apply-event`、`/rl_sessions/{id}/personality`。
- `POST /event/choose`（localhost）→ **HTTP 200**，回傳完整 JSON（選項、lean_prob、chosen_action、outcome）。
- `POST http://172.31.143.82:8000/event/choose`（Godot 實際使用的 WSL IP）→ **HTTP 200**。

→ 前端「面對事件」應已能正常取得分身選擇結果。請在 Godot 內重按一次確認。

## 3. 本次故障：寫遺言（SBERT 人格分析）遇到網路錯誤:2

### 症狀
玩家在「寫遺言」畫面送出文字，`PersonalityInferClient` 收到
`result == HTTPRequest.RESULT_CANT_CONNECT (= 2)`，  
於 `_on_completed`（`PersonalityInferClient.gd`）發出 `infer_failed("網路錯誤：2")`，
Godot console 出現對應錯誤。

### 根因
後端進程已不存在（崩潰或被關掉）。`RESULT_CANT_CONNECT` 代表 TCP 連線直接被拒（Connection refused），
與 404（服務在但路由不存在）不同：這是**服務完全沒在聽 port 8000**。

```
pgrep -af "api.server"   →  無輸出（或只剩殭屍）
ss -tlnp | grep 8000     →  無輸出
curl http://172.31.143.82:8000/health  →  exit 7 (curl: (7) Failed to connect)
```

### 解決方式
在 WSL 內重新啟動後端，**必須帶 `P7H_OUT_DIR`** 以確保寫入正確的真人收案目錄：

```bash
cd /home/user/personality-dungeon
P7H_OUT_DIR=reports/experiments/p7h_real_study \
  ./venv/bin/python -m api.server &>> logs/api_server.log &
echo "PID $!"
```

等待約 3 秒（SBERT 模型首次呼叫時才懶載入，約需 10 秒）後確認：

```bash
# 確認 port 已開
ss -tlnp | grep 8000

# 確認 SBERT 端點可用（首次約 10 秒，之後快）
curl -s --max-time 15 http://172.31.143.82:8000/personality/infer_sbert \
  -X POST -H "Content-Type: application/json" \
  -d '{"text":"我想冒險探索世界"}' | python3 -m json.tool
```

預期回傳：含 `"vector": {...9 traits...}` 的 JSON，`model: "sbert-mlp-v7"`。

### 結果（已驗證，2026-06-08）
重啟後 SBERT 端點正常回應，Godot 遺言分析流程恢復正常。

## 4. 之後若再遇到 404 / 連不上，排查順序

**先判斷是哪一層錯誤（口訣）：**

| Godot `result` 值 | 意義 | 常見原因 |
|---|---|---|
| `RESULT_CANT_CONNECT = 2` | TCP 連線被拒 | 後端沒跑、port 未開、IP 錯誤 |
| `RESULT_SUCCESS = 0` + `response_code == 404` | 有連上但路由不存在 | server.py 版本過舊、路徑拼錯 |

**排查步驟：**

1. **後端有沒有在跑？** `ss -tlnp | grep 8000`。沒有 → 用第 3 節的指令啟動（記得帶 `P7H_OUT_DIR`）。
2. **改過 `server.py` 後有沒有重啟？**（最常見的 404 原因）route 是程式啟動時載入，改檔不會熱生效（除非用 `--reload`）。
3. **IP 對不對？** WSL2 的 IP **每次重開機可能改變**。用 `hostname -I` 重新確認，必要時更新 Godot client 的 `api_base_url`。
   - 長期建議：把 `api_base_url` 抽成單一 autoload 常數，避免 8 個 `.gd` 各自硬寫。
4. **路徑拼對嗎？** 拿 `curl -s http://127.0.0.1:8000/openapi.json | python3 -c "import sys,json;print('\n'.join(sorted(json.load(sys.stdin)['paths'])))"` 列出所有實際路由比對。
5. **SBERT 首次呼叫需 ~10 秒**（懶載入模型）。timeout 設太短（< 15 秒）也會讓 Godot 看到連線失敗。

## 5. 附帶釐清：「人格事件觸發」的 9D 數值與紅綠變化是固定的嗎？

**不是固定 / 寫死的**，但目前的後端設計會讓它「看起來」變化不大，需分兩層理解：

### (a) 紅綠顏色 — 動態，依 delta 正負決定
`EventNotificationPanel.gd:79-82`：每個維度的 delta 是
- **正值 → 綠色** `Color(0.4, 1.0, 0.4)`
- **負值 → 橘紅** `Color(1.0, 0.5, 0.4)`

顏色完全由該步的 `feature_deltas` 正負號即時決定，不是寫死的。

### (b) 9D delta 數值 — 來自後端動態計算，非前端常數
資料流：
```
BifurcationController.request_sequence_now / 自動觸發
  → POST /bifurcation/sequence  (帶 personality_vector, n_steps, group, intensity)
  → 後端 event_sequence_planner() 依目前人格向量 + 組別方向計算每步 feature_deltas
  → 回傳 sequence → EventSequencePlayer 逐步 emit step_applied(deltas)
  → EventNotificationPanel 顯示
```
- delta 由 `api/server.py:1109 /bifurcation/sequence` 的 `event_sequence_planner` 依**當前人格向量**計算，方向由組別決定（`experiment` = v1 敏感方向、`control` = 隨機方向，見 `BifurcationController.gd:37` 與 `_direction_mode_for_group`）。
- 所以理論上每次人格不同、數值就不同，**不是前端常數**。

### (c) 為什麼實測「看起來像固定」— 已知的裝置問題（非顯示 bug）
研究日誌與記憶（`p7h-apparatus-broken`）記錄了根因：事件強度受 **proximity 調制**，越接近分岔施力越小；當 proximity 飽和（→1.0）時，對齊事件退化成 **min nudge ≈ 0.0005/step**，每維 ±0.0002 經 clamp 後幾乎為 0。
- `EventNotificationPanel.gd:70` 還會把 `abs(val) <= 1e-4` 的維度濾掉不顯示，於是面板可能只剩極少數維度、且數值很小、每次相近 → 視覺上「像固定」。
- 這是 **Space A/B 座標未對帳 + proximity 飽和** 的後果，屬於正在處理的裝置問題，**不是顏色或數值寫死**。後端 Space A/B 雙射已於 commit `8508266` 落地，前端 Space-B 顯示映射仍待與後端對帳（見記憶 `p7h-apparatus-broken`）。

> 小結：紅綠 = 依正負動態；9D 數值 = 後端依人格動態算出；目前數值偏小且相近是 proximity 飽和 / 座標未對帳所致，不是寫死。
